## 构建与环境

### 报 "Could not create named generator Visual Studio 18 2026"
- 原因：PATH 上的 CMake 3.27 不认识 VS 2026 的生成器。
- 处理：改用 VS 自带的 CMake 4.3+：
  ```powershell
  & "C:\Program Files\Microsoft Visual Studio\18\Community\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe" --preset vs2026
  ```

### 报找不到 vcpkg / toolchain file
- 确认 `VCPKG_ROOT` 已设置，并且是**新开的** shell：
  ```powershell
  $env:VCPKG_ROOT = 'C:\Program Files\Microsoft Visual Studio\18\Community\VC\vcpkg'
  ```
- 确认路径下存在 `scripts/buildsystems/vcpkg.cmake`。

### 首次配置长时间停在 "Fetching registry information"
- 原因：vcpkg 需要从 GitHub 拉 registry 与源码，直连受限时会挂起。
- 处理：给 git 配代理后再配置（不改仓库内任何配置）：
  ```powershell
  $env:GIT_CONFIG_COUNT=3
  $env:GIT_CONFIG_KEY_0='http.proxy';    $env:GIT_CONFIG_VALUE_0='http://127.0.0.1:7890'
  $env:GIT_CONFIG_KEY_1='http.version';  $env:GIT_CONFIG_VALUE_1='HTTP/1.1'
  $env:GIT_CONFIG_KEY_2='http.lowSpeedLimit'; $env:GIT_CONFIG_VALUE_2='1000'
  ```
  大 pack 经代理逐块停滞时应加 `http.version=HTTP/1.1` 与 `http.postBuffer=524288000`。

### 链接阶段找不到 OpenGL/XInput/winmm 符号
- `glad` 与 `glfw3` 由 vcpkg 提供，检查 `find_package(glad CONFIG REQUIRED)` 是否被误删；`Xinput`/`winmm` 随 `MooApplicationCore` 在 Win32 下链接，不要重复手写 `-l` 参数。

### 中文注释乱码或大量按字符集的警告
- CMake 已在 MSVC 下固定 `/utf-8`；不要另加 `/source-charset` 或把源码存成带 BOM/GBK。

### 新增公共头后配置失败 "Duplicate public header basename"
- 公共头只按文件名（不含目录）唯一。重命名冲突的头，或确认后登记到 `MOO_PUBLIC_HEADERS`。

### 新增 .cpp 后链接报重复定义
- 不要把 `Source/Legacy/*.hpp` 或 Sandbox 下的 `.inl` 包含进新的编译单元：Legacy 头含大量非 inline 定义，只允许 `Source/Sandbox/Private/SandboxScene.cpp` 包含。

## 启动与资源

### 控制台提示 "resource dir not found, falling back to ../resources"
- `MOOLAB_RESOURCE_DIR` 是配置时的源码绝对路径；工程被移动/改名后需要重新配置并编译。
- 回退路径是进程工作目录相对的 `../resources/`，从 `build/vs2026/Release/` 启动时可用；从其他目录启动会找不到资源。

### 启动即退出 / 若干资源加载失败
- 检查必需文件是否齐全：`character.bin`、`database.bin`、`long_motion.bin`、`foot_contacts.bin`、`skybox.png`、`BRDFLut.png`、`EavgLut.png`、`UI/*.png`。
- `foot_contacts.bin` 与 `long_motion.bin` 有强绑定：标签帧数与源动作不一致、或哈希（long_motion.bin 全字节 FNV-1a64）不匹配都会校验失败。重新烘焙用 `FootContactBake`（`--target` 构建）。

### 着色器相关启动失败
- 着色器从 `MOOLAB_SHADER_DIR`（配置时的 `Shaders/` 绝对路径）读取；打开或编译失败会明确报错退出。检查 `Shaders/` 是否完整、是否移动过工程。

### 运行时报 GL 上下文相关断言
- 所有 GL 资源（`GpuRenderer`、`CpuImagePresenter`）必须在 `FAppWindow` 之后构造、之前析构，且只在主线程使用。不要在别的线程创建窗口或 GL 对象。

### 无显示环境想跑截图
- `--hidden` 只是隐藏 GLFW 窗口，仍需要可用的 GL 4.6 上下文；真正的无显示服务（如 CI 容器）当前不支持。

## 渲染问题

### GPU 与 CPU 截图差异超出阈值
- 先确认用的是同一批资源与同一个 exe：`MooImageDiff` 对 `gpu_060.png` / `cpu_060.png` 应通过（差 >32 占比 ≤0.5%）。
- 若整体亮度/颜色偏移，检查 PBR 常量表与 `Shaders/pbr_common.glsl` 是否与 `Source/Runtime/Renderer/PbrShading.*` 一致。
- 若边缘锯齿/纹理错位，注意 GPU 路径**刻意保留**的非标准行为：非透视插值、UV 互换、最近邻采样、F0 = albedo、观察空间深度。改变这些"修正"会让对拍失败。
- 差异只在少数像素：确认截图帧号一致（`--capture-frame 60` 是第 60 帧，从 0 开始），且都用了 `--unlimited-fps`。

### 画面全黑 / Viewport 空白
- 检查是否误开了"角色皮肤默认不绘制"以外的显示开关；Viewport 是离屏 720×720 等比留边显示，窗口最小化时帧缓冲尺寸为 0。
- GPU 模式看 `Gpu` 时间戳是否始终为 0（未就绪），CPU 模式该值恒为 0 属正常。

### CPU 模式截图与历史哈希不同
- 基准哈希依赖 OpenCV 版本与资源内容。README 记录的 `F32E92295DFD7FFF` / `6CC141F39195243E` 是 OpenCV 4.14.0 + 重烘焙后的 `foot_contacts.bin`；换 OpenCV 或重新烘焙资源都会变。确属预期时同步更新 README 与 CHANGELOG。

## 仿真与动画问题

### 角色穿模或抖动
- 调小接触 eps、减小子步时间步、增大子步数；检查胶囊半径/长度是否与动作尺度匹配。
- 力矩控制的截止步与增益过高会放大抖动，先在编辑器属性里降增益再排查。

### Physics 场景"重置后与历史帧不一致"
- 用 `SceneProbe` 检查：它比对 Physics 重置/模式往返的历史帧、暂停/单步与 MM 边界，退出码 0 通过、1 硬失败、3 预算失败。

### 无法进入 Motion Matching
- MM 需要 `long_motion.bin` 与 `database.bin` 校验通过；失败时 UI 会显示原因并禁止进入，Physics 仍可用。检查文件是否被替换、帧数或哈希是否变化。

### 脚部 IK 结果异常
- `foot_contacts.bin` 的逐脚标签是 IK 的输入，标签错位会直接表现为脚下滑或悬空；确认烘焙工具与 `long_motion.bin` 同源。

## 性能问题

### `Cost` 很高但 `Gpu` 接近 0
- `Cost` 覆盖窗口消息、编辑器 UI、仿真、渲染提交与截图写盘，**不包含**节流等待；GPU 提交是异步的，`Gpu` 与 `Cost` 不能相加也不能互相替代。
- 60 帧节流下 `Interval` 约 17ms 属正常，不要用 1/Interval 推断性能提升。

### CPU 占用高
- 设置 `OMP_WAIT_POLICY=PASSIVE` 可显著降低忙等占用（等效核数从十几个降到 1 左右）；这是运行库策略，程序未写死默认。
- 编辑器 UI 每帧重建也有固定成本，`Cost` 已包含；对比历史数据时注意窗口层不同（1.x 是 OpenCV highgui）。

### 想定位热点
- 用 `python Tools\Verify\verify_gl.py perf` 做 3×600 帧；再用 VS 诊断工具/ETW 看 `Cost` 各段。

## 验证工具用法

| 命令 | 作用 | 说明 |
| --- | --- | --- |
| `MooImageDiff a.png b.png` | 像素对拍 | 差 ≤3 占比 ≥99%、差 >32 占比 ≤0.5%；退出码 0/1/2/3 |
| `verify_gl.py capture` | 截图 + 历史哈希 + 对拍 + CLI 退出码 | 需 Python + Pillow，输出在 `build/vs2026` |
| `verify_gl.py probe` | GL 探针与 4 个故障用例 | 先跑 `Tools\Verify\compile_gl_probe.cmd` |
| `verify_gl.py perf` | 性能采样 | 3×600 帧 |
| `SceneProbe <前缀>` | 场景语义回归 | `--target SceneProbe` 构建，退出码 0/1/3 |

负对照：`gpu_060.png` 对 `cpu_300.png` 必须失败，否则说明对拍阈值或截图流程有问题。
